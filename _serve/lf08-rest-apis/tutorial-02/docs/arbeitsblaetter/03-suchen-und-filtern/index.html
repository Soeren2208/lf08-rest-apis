AB 03 – Suchen, filtern und blättern

Die Situation​

Das Gästebuch läuft seit einigen Wochen. Zwei Rückmeldungen kommen herein:

„Die ältesten Einträge stehen oben. Wir wollen die neuesten zuerst sehen."

„Für den Jahresbericht brauchen wir alle Einträge aus einem bestimmten Jahr."

Und die Kollegin aus dem Betrieb ergänzt: „Habt ihr euch überlegt, was passiert, wenn da irgendwann 10.000 Einträge drin stehen?"

Lernziele​

Nach Bearbeitung dieses Arbeitsblatts kannst du:

  • abgeleitete Abfragen aus Methodennamen erzeugen und ihre Funktionsweise erklären
  • begründen, warum Filtern und Sortieren in die Datenbank gehört und nicht in den Controller
  • Request-Parameter mit @RequestParam entgegennehmen und optional gestalten
  • eine Schnittstelle mit Pageable seitenweise ausliefern
  • den Aufbau einer Page-Antwort lesen

Aufgaben​

Aufgabe 1 – Die falsche Reihenfolge​

Die Einträge erscheinen in der Reihenfolge ihrer Ids — der älteste zuerst. Für ein Gästebuch ist das genau verkehrt herum.

Eine naheliegende Lösung wäre, im Controller zu sortieren:

@GetMapping
public ResponseEntity<List<GuestbookEntry>> findAllEntries() {
    List<GuestbookEntry> alle = repository.findAll();
    alle.sort(Comparator.comparing(GuestbookEntry::getDate).reversed());   // ❌
    return ResponseEntity.ok(alle);
}

Das funktioniert. Trotzdem ist es der falsche Weg.

Warum das schlechter Stil ist

Die Datenbank kann sortieren — schnell, und mit Unterstützung durch Indizes. Hier holt sich die Anwendung alle Datensätze, überträgt sie über die Datenbankverbindung in den Hauptspeicher und ordnet sie dann selbst neu.

Bei zwanzig Einträgen fällt das nicht auf. Bei zwanzigtausend schon.

Faustregel: Arbeit, die die Datenbank erledigen kann, gehört in die Datenbank.

Aufgabe 2 – Sortieren lassen​

Spring Data nimmt Sortierwünsche direkt entgegen. Dafür gibt es das Interface Sort:

repository.findAll(Sort.by(Sort.Direction.DESC, "date"));

Daraus erzeugt Hibernate ein ORDER BY date DESC — die Datenbank sortiert, nicht dein Programm.

Nach date sortieren, nicht nach id

Beides liefert hier zufällig dasselbe Ergebnis, weil neuere Einträge auch höhere Ids haben.

Fachlich richtig ist date: Gefragt war „die neuesten zuerst" — und das ist eine Aussage über das Datum. Würden Einträge später einmal nachträglich importiert, liefe die Sortierung nach id ins Leere.

Aufgabe 3 – Einträge eines Jahres​

Jetzt der zweite Wunsch: alle Einträge eines bestimmten Jahres. Das Jahr soll der Client in der URL mitgeben:

GET /api/v1/guestbook?year=2026

Alles nach dem ? ist ein Request-Parameter. Im Unterschied zur Pfadvariablen bezeichnet er keine eigene Ressource, sondern schränkt eine vorhandene ein.

PfadvariableRequest-Parameter
Beispiel/guestbook/**7**/guestbook?**year=2026**
Annotation@PathVariable@RequestParam
Bedeutungwelche Ressourcewie eingeschränkt
Pflicht?ja, Teil des Pfadesmeist optional
@GetMapping("/jahr")
public ResponseEntity<List<GuestbookEntry>> findByYear(@RequestParam Integer year) {
    List<GuestbookEntry> gefiltert = repository.findAll().stream()
            .filter(entry -> entry.getDate().getYear() == year)
            .toList();
    return ResponseEntity.ok(gefiltert);
}
Dasselbe Problem wie in Aufgabe 1 — nur schlimmer

repository.findAll() holt jeden einzelnen Eintrag aus der Datenbank. Anschließend wirft der Filter die meisten davon weg.

Bei 10.000 Einträgen und der Frage nach dem Jahr 2019 werden 10.000 Datensätze übertragen, um vielleicht 30 zu behalten.

Sieh dir das erzeugte SQL im Log an: Dort steht ein schlichtes select ... from guestbook_entry — ohne where. Die Datenbank weiß gar nicht, dass gefiltert werden soll.

Aufgabe 4 – Die Abfrage ins Repository verlagern​

Spring Data kann die Abfrage aus dem Methodennamen ableiten. Du schreibst nur die Signatur — die Implementierung entsteht beim Start.

List<GuestbookEntry> findByDateBetween(LocalDateTime from, LocalDateTime to);

Mehr nicht. Kein Rumpf, kein SQL.

So liest Spring Data den Namen:

findBy      Date        Between
────────    ────        ───────
"suche"     Attribut    Vergleich
            date        between ? and ?

Daraus wird ... where date between ? and ?.

Lass dir die Möglichkeiten zeigen

Tippe im Repository findBy und warte auf die Vorschlagsliste deiner Entwicklungsumgebung. Sie kennt die Attribute deiner Entität und schlägt gültige Fortsetzungen vor — findByAuthor, findByTitleContaining, findByDateAfter und viele mehr.

Eine Übersicht steht im Infoblatt Abgeleitete Abfragen.

LocalDateTime from = LocalDate.of(year, 1, 1).atStartOfDay();
LocalDateTime to   = from.plusYears(1);

Aufgabe 5 – Ein Endpunkt statt zwei​

Du hast jetzt zwei Endpunkte: /guestbook und /guestbook/jahr. Das ist unnötig.

Überleg einmal fachlich: Beide beantworten dieselbe Frage — „gib mir Gästebucheinträge". Der zweite schränkt sie nur ein. Das ist kein eigener Anwendungsfall und verdient deshalb keine eigene Adresse.

@GetMapping
public ResponseEntity<List<GuestbookEntry>> findAllEntries(
        @RequestParam(required = false) Integer year) {

    if (year == null) {
        return ResponseEntity.ok(repository.findAll(Sort.by(Sort.Direction.DESC, "date")));
    }

    LocalDateTime from = LocalDate.of(year, 1, 1).atStartOfDay();
    LocalDateTime to   = from.plusYears(1);
    return ResponseEntity.ok(repository.findByDateBetween(from, to));
}

Jetzt beantwortet ein Endpunkt beide Fälle:

GET /api/v1/guestbook              →  alle Einträge
GET /api/v1/guestbook?year=2026    →  nur die aus 2026
Was passiert ohne required = false?

Dann ist der Parameter Pflicht. Ein Aufruf ohne ?year=… würde mit 400 Bad Request abgewiesen.

Probiere es ruhig aus: Lass required = false einmal weg und rufe den Endpunkt ohne Parameter auf.

Aufgabe 6 – Seitenweise ausliefern​

Bleibt die Frage der Kollegin: Was bei 10.000 Einträgen?

Auch dann liefert dein Endpunkt alle auf einmal. Die Antwort wäre mehrere Megabyte groß, der Browser des Kunden würde spürbar hängen. Echte APIs liefern deshalb Seiten.

Spring Data bringt das mit: Statt einer List gibt man eine Page zurück und nimmt ein Pageable entgegen.

Page<GuestbookEntry> findByDateBetween(LocalDateTime from, LocalDateTime to, Pageable pageable);
@GetMapping
public ResponseEntity<Page<GuestbookEntry>> findAllEntries(
        @RequestParam(required = false) Integer year,
        @PageableDefault(size = 10, sort = "date", direction = Sort.Direction.DESC)
        Pageable pageable) {

    if (year == null) {
        return ResponseEntity.ok(repository.findAll(pageable));
    }

    LocalDateTime from = LocalDate.of(year, 1, 1).atStartOfDay();
    LocalDateTime to   = from.plusYears(1);
    return ResponseEntity.ok(repository.findByDateBetween(from, to, pageable));
}

Das Pageable trägt drei Angaben: welche Seite, wie groß, wie sortiert. @PageableDefault legt die Werte fest, falls der Client nichts angibt — dadurch ist auch die Sortierung aus Aufgabe 2 mit erledigt.

Der Client steuert es über Parameter:

GET /api/v1/guestbook?page=0&size=5
GET /api/v1/guestbook?page=1&size=5&sort=author,asc
GET /api/v1/guestbook?year=2026&page=0&size=20

Die Antwort sieht jetzt anders aus:

{
  "content": [ { "id": 4, "title": "...", "author": "..." } ],
  "totalElements": 4,
  "totalPages": 4,
  "number": 0,
  "size": 1,
  "first": true,
  "last": false
}
FeldBedeutung
contentdie Einträge dieser Seite
totalElementswie viele es insgesamt gibt
totalPageswie viele Seiten das ergibt
numberdie aktuelle Seite, beginnend bei 0
sizewie viele pro Seite
first / lastob dies die erste bzw. letzte Seite ist
Die Antwortstruktur hat sich geändert

Vorher kam ein Array, jetzt ein Objekt mit den Einträgen unter content. Ein Client, der bisher direkt über die Antwort gelaufen ist, muss angepasst werden.

Genau deshalb überlegt man sich Paginierung früh — ein späterer Umbau trifft alle Clients.

Zusammenfassung​

Das hast du gelernt
  • Sortieren und Filtern gehören in die Datenbank, nicht in den Controller.
  • Abgeleitete Abfragen entstehen aus dem Methodennamen: findByDateBetween wird zu where date between ? and ?.
  • @RequestParam nimmt Werte aus der URL entgegen; required = false macht sie optional.
  • Ein Filter rechtfertigt keinen eigenen Endpunkt — er schränkt eine vorhandene Ressource ein.
  • Pageable und Page liefern Ergebnisse seitenweise; @PageableDefault setzt Standardwerte.
  • Eine Page-Antwort ist ein Objekt mit content, totalElements, totalPages und number — kein Array mehr.
  • Im Log lässt sich am erzeugten SQL überprüfen, ob die Arbeit wirklich in der Datenbank passiert.

Selbstkontrolle​

  1. Warum ist Sortieren im Controller schlechter Stil?
  2. Wie wird aus findByDateBetween eine SQL-Abfrage?
  3. Wann nimmt man eine Pfadvariable, wann einen Request-Parameter?
  4. Warum bekommt der Jahresfilter keinen eigenen Endpunkt?
  5. Welchen Wert hat number auf der ersten Seite?
  6. Woran erkennst du im Log, dass die Datenbank filtert und nicht dein Programm?
Antworten
  1. Weil die Anwendung dafür alle Datensätze aus der Datenbank holen und in den Hauptspeicher übertragen muss. Die Datenbank kann das schneller und mit weniger Datenverkehr.
  2. Spring Data zerlegt den Namen beim Start: findBy leitet die Abfrage ein, Date benennt das Attribut, Between den Vergleich. Daraus entsteht where date between ? and ?.
  3. Eine Pfadvariable bezeichnet welche Ressource gemeint ist (/guestbook/7). Ein Request-Parameter schränkt eine Sammlung ein (?year=2026).
  4. Weil er keinen neuen Anwendungsfall darstellt. Gefragt sind weiterhin Gästebucheinträge — nur eine Teilmenge davon. Deshalb dieselbe Adresse mit optionalem Parameter.
  5. 0. Die Zählung beginnt bei null.
  6. Das erzeugte SQL enthält eine where-Bedingung. Fehlt sie und es steht nur select ... from guestbook_entry, wurde die ganze Tabelle geholt und erst danach gefiltert.
